# L11 Steam 発売の戦略（改訂版）

元の案: `raw/1-diverge/L11-steam.md`。批評: `raw/2-critique/L11-steam.md`（システムデザイナー × 戦闘の手触りと読み合い）。

改訂で確かめたこと:

- `docs/GLOSSARY.md` 453 行: 「看板」は拠点の飾り（名乗っている称号の看板、`HubDecor`）として使用済み。元の「看板一句」は改名する
- 「総崩れ」は実装済みの結びの祝福（boons-expansion U09）。元の「総崩れ」は改名する
- `src/meta/unlocks.ts` 16 行: `UnlockCondition` は `start / chapterBoss / quest` の 3 形
- `src/meta/quests.ts`: 依頼はラン開始時に 1 つ受け、`state.questRun` の `QuestCounters`（`counters`・`justDodges`・`staggers`・`bursts`・`reactions` など）をラン中に数える。**数えるのはラン 1 本ぶん**で、ランをまたいだ累計は持たない
- 「口上」「手合」「見得」「読み筋」「旗倒れ」「開帳」「栞」はコードと資料に未使用

## 議論の結論（全体の順序）

批評の根本の指摘を受け入れる。**「黄は打て、赤は返せ」は今のゲームでまだ本当になっていない**（S1: bot が狙わずにカウンターが 60 秒に 50〜95 回出る。完遂率 25〜50%。ヒットストップ 20〜35%）。そこで案を 3 つの段に並べ直した。

1. **今すぐ・発売の段取りに依らない**: 混成操作・目安箱・読み筋・訳語台帳の段 0。どれも戦闘の核の段を助けるか、後でやると高くつく物
2. **戦闘の核の段を通った後**: 口上（の検分の門）を通してから、初陣・一章体験・濃淡予告・旗倒れ・絵巻起こし・撮影台
3. **EA の前後**: 出店支度・手合・免状・開帳・栞

ストアのリーダーボードは単一の並びなので、原則の例外は「手合」1 つに絞る（批評の問 8）。全 21 階のランは並べない。

### 口上
- 種別: 基盤
- 領域: presentation
- 一言: 「黄は打て、赤は返せ」を約束として、ストア・トレーラーの最初の 5 秒・最初の 3 分の遊びに通す。ただし先に、計測でその約束が本当かを確かめる門を置く。
- 仕組み:
  - **段 1: 約束の検分**（門）。`qa:probe` に「約束」の節を 1 つ足す。同じ陣に対し、3 通りの bot を当てる
    - 予告を読む bot: 黄で殴り、赤で受け流す
    - 連打の bot: 予告を見ずに殴り続ける
    - 避ける bot: 予告を見て下がるだけ
  - 門の基準の目安: 読む bot が連打の bot より「撃破までの時間が 3 割短く、被弾が半分以下」。連打の bot のカウンターの数が、読む bot の半分以下。これを満たすまで、ストアの文言・トレーラー・体験版の最初の陣を確定しない（基準を満たす設計そのものは戦闘のレーンの仕事）
  - **段 2: 約束を置く 4 か所**。ストアの短い説明の 1 行目、カプセルの絵、トレーラーの 0〜5 秒、体験版の最初の陣。英語は 2 拍の対（例 `Read yellow, strike. Read red, return.`）を訳語台帳と同時に決める
  - ストアのタグは Action Roguelike / Hack and Slash / Pixel Graphics / Loot を柱にし、`Bullet Hell`・`Auto Battler`・`Souls-like` のような外れた期待を呼ぶ物は付けない
  - スクリーンショット 5 枚は、1 枚に 1 つの約束（返し・旗倒れ・反応の連鎖・装束と紋・門前町）
- なぜこのゲームで: 予告の 2 色と受け流しは全部の敵で揃えてある。オート攻撃・自動照準の禁止は、そのまま「Survivors 系とは違う」の宣言になる。約束を世界観（和風）でなく操作に置くのは、和の地下に西洋の怪物がいる食い違い（S6）をストアで突かれないため
- 着想元: Chris Zukowski の「最初の 5 秒でジャンルの信号を出す」。そこから、ジャンル名でなく「操作の約束」を看板にし、さらにその約束を bot の計測で門にする形に変えた（約束を計測で守る例は他作に見当たらない。決定性と bot がある、このゲームの体制だからできる）
- 安っぽくならないための要点 / リスク:
  - 門を通さずに文言を先に出すと、体験版の 10 分で「言っていることと違う」になる。これが最大のリスク
  - カプセルの絵は高解像度の 1 枚絵で、コード内ピクセルマップの方針がストアの絵まで及ぶかは未決。外注するかをユーザーに聞くのが最初の問い。案の中で絵の構図は決めない
- 議論で変わった点: 「看板」が拠点の飾りの名前と衝突するので改名。批評の「約束の検証が無い」を受け、`qa:probe` の 3 通りの bot による門を段 1 として足した
- 規模: S（段 1 の計測）+ 段 2 はユーザーの判断待ち

### 初陣
- 種別: 新要素
- 領域: ux
- 一言: 最初のランの地下 1 階だけを、手描きで決定的な階にする。陣の並びで「黄・赤・大将」を文字なしで、しかも「殴り続けると痛い」の対比で教える。
- 仕組み:
  - 条件は探索履歴が 0 件。保存値は足さない。器は主の間の手描きの格子（`src/map/layout/lordHallGrids.ts`）
  - 陣は 4 つを一本道に並べる
    - 1 の陣（**黄と赤の対比**）: 予備動作の長い並 3 体の中に、赤で必ず振り切る 1 体を混ぜる。黄の間に殴れば止まり、赤になっても殴り続けた人だけが被弾する。「黄の間に殴る」より「赤では殴っても止まらない」を体で知る
    - 2 の陣（**受け流しと空振り**）: コミットの速い突撃 1 体の後ろに、遅い追撃の 1 体。受け流しを当てれば即怯み、外すと 0.35 秒の硬直に追撃が当たる
    - 3 の陣: 大将付きの陣。大将を討つと崩れ、群勢・敗走を見せる（下の「旗倒れ」の絵がここで初めて出る）
    - 4 の陣: 地形の油と火の敵。反応を見せる
  - 説明は Tips ノートの頁が開くだけ（「新しい頁」の印）。入口の札は「地下 1 階・初陣」だけ
  - 門前町の稽古場（`meta/hub.ts` の `training`）から何度でも入り直せる。上級者が新しい型を試す場にもなる
- なぜこのゲームで: S1 は「黄なら殴れ、赤なら受け流せ」が Tips と予告の図解にしか無いと指摘している。決定性があるので、教えたい瞬間が毎回同じ形で起きる。初見の死亡が深度 3 に集中する（S4・S7）前に読みを渡す
- 着想元: Hades の最初の部屋、Celeste の文字なしの面構成。チュートリアルの画面でなく「陣形そのものが教材」の形に変え、さらに「正解を見せる」でなく「間違いが痛い対比」で教える
- 安っぽくならないための要点 / リスク:
  - 敵の名札や台詞で説明しない。2 回目以降に強制しない
  - 1 ラン目の 3 分以内に 1 の陣へ着くこと（配信者がタイトルから 3 分で山場を見せられるか）
  - 口上の門を通る前に作ると、教える中身が後で変わる
- 議論で変わった点: 批評の指摘どおり、今は黄の間のカウンターが勝手に起きるので、1 の陣の役目を「赤で殴り続けると痛い」の対比へ移し、2 の陣に空振りを咎める追撃を足した
- 規模: M

### 混成操作
- 種別: 改善
- 領域: platform
- 一言: パッドのボタンとマウスの照準を同時に使えるようにし、Steam Deck のジャイロで自動照準なしの正確な照準を成立させる。Deck の画面での見え方も同時に確かめる。
- 仕組み:
  - 今の `InputController.snapshot`（`src/core/input.ts` 598〜624 行）は、ボタン押下でも `pad.active` が true になり、マウスを動かしていないフレームは照準元がパッドへ戻る。右スティックが中立なら照準は null。ジャイロ → マウスで照準している人は、ボタンを押した瞬間に照準が消える
  - 直し方: 照準元をパッドへ切り替えるのは「右スティックを倒した時」だけ。ボタン・左スティックでは切り替えず、最後のマウス位置を照準に残す
  - テストで「ボタン連打・左スティック移動の間もマウスの照準が保たれる」を固定する
  - Steam Input の推奨配置（左手側にダッシュ・受け流し・瓶、ジャイロは右パッドに触れている間だけ）を公式の配置として出す
  - **Deck の 1280×800 での見え方**: 480×270 は 2.67 倍の非整数倍で入る。`map:shot` に Deck の解像度の場面を 1 つ足し、ドット絵のにじみ・欠けと、最小の字が 9px を割らないかを確かめる。整数倍（2 倍 = 960×540 を中央に置く）と、にじみを許す拡大のどちらにするかは、撮った絵を見て決める
- なぜこのゲームで: 原則は自動照準の禁止。パッドの照準の答えは吸着でなくジャイロであるべきで、今の切り替えはその唯一の答えを壊している。左手で完結するキー配置はパッドの左半分にそのまま写る
- 着想元: Steam Deck の Verified の基準と Steam Input。Deck の遊んだ時間は Steam 全体の約 2.75%、インディーの発売時の売上の約 1 割、という報告
- 安っぽくならないための要点 / リスク: 決定性には触らない（入力の組み立ては step の外）。マウスとパッドの照準の取り合いを起こさない
- 議論で変わった点: 批評がコードで実害を確認。Deck の非整数倍の確認（批評の問 5）を同じ案に入れた
- 規模: S

### 目安箱
- 種別: 基盤
- 領域: platform
- 一言: 1 キーで「今のランの棋譜・版・設定・ひとことのメモ」を 1 つのファイルにまとめ、開発側はその版のコードで同じフレームまで再生できる。環境をまたいだ決定性の確認もここで始める。
- 仕組み:
  - ポーズ画面に「目安箱」を置く。押すと次を 1 つの JSON にまとめ、`BOKUEN/reports/` に書く
    - ランの開始からのリプレイ
    - `APP_VERSION`・`REPLAY_VERSION`・`BALANCE_HASH`・OS の種類（Windows / Linux）
    - 設定
    - ひとことの入力欄（クリップボードからの貼り付けで受ける。IME をゲームの中で受けない）
  - 落ちた時は main プロセスが最後の棋譜を `.crash-` の名前で書き残す
  - 受け取り側の手順を 1 本のスクリプトにする: 報告の `APP_VERSION` のタグ（`scripts/bump.mjs` が打っている）を worktree に出し、そこで再生して止めたいフレームまで回す。`BALANCE_HASH` の不一致は拒否でなく警告の 1 行
  - **環境をまたぐ決定性の確認**（批評の問 4）: 同じ棋譜を Windows と Linux（Deck）で回し、結果のハッシュが一致するかを発売前に 1 回確かめる。三角関数などの浮動小数点の差がここで見つかる。見つかれば、目安箱・手合のどちらも直す前に止まれる
- なぜこのゲームで: 決定性があるので「再現できない不具合」がほぼ消える。個人 + AI の並列開発で EA を回すとき、報告の質が開発の速さを決める。`hitch:probe` や QA の bot と同じ道具立てに乗る
- 着想元: 江戸の目安箱。Factorio の決定性を使った不具合の再現。それをプレイヤーが 1 キーで出せる形にし、受け取り側の「その版で再生」までを道具にした
- 安っぽくならないための要点 / リスク:
  - パス・名前など個人の情報を含めない。倉庫全体は出さない（棋譜の装備のスナップショットだけ）
  - 版が違うまま黙って再生してずれるのが最悪。版の照合を必ず先に通す
- 議論で変わった点: 受け取り側の「タグを worktree に出して再生」までを含め、環境をまたぐ決定性の確認（Win と Deck）をこの案の役目に足した
- 規模: S

### 読み筋
- 種別: 新要素
- 領域: ux
- 一言: リプレイの再生の時だけ、敵ごとの黄・赤・攻撃の時間の帯と、自分の受け流しの窓を譜面のように重ねて見せる。遊んでいる最中には出さない。
- 仕組み:
  - 探索履歴のリプレイの再生に「読み筋」の切り替えを置く。入れると、各敵の足元に予備動作の帯（黄の長さ・赤の長さ）が出て、今どこにいるかが進む
  - プレイヤーの下には、受け流しの窓・ダッシュの無敵・見切りの成立が帯として出る
  - こま送りで「赤に入って何フレーム目で返したか」「黄の何割の所で割り込んだか」が見える。数字はこま送りの時だけ小さく
  - 描画だけの層で、state を読むだけ（不変条件 1）
- なぜこのゲームで:
  - 戦闘の核は読みなのに、上手い人の手は速すぎて見えない。決定性のある再生とこま送りがあるので、帯は追加の記録なしで描ける
  - Tips ノートの予告の図解（`render/telegraphDiagramUi.ts`）を、実戦の上に重ねた形。説明を UI に書かない原則のまま、上達の道具になる
  - 開発側にも効く。S1 の「カウンターが自然に出る」「完遂率 25〜50%」の原因を、人の目で確かめる道具で、口上の門の作業を直接助ける
- 着想元: Street Fighter 6 のフレームメーター、音楽ゲームの判定の帯。格闘ゲームは練習の最中に出すが、ここでは再生の時だけに限り、遊びの最中の読みを奪わない
- 安っぽくならないための要点 / リスク: ライブの遊びへ持ち込みたくなる誘惑を原則として断つ。帯の色は予告の線と同じ文法にし、別の色の意味を増やさない
- 議論で変わった点: 批評の派生案から取り込んだ（出典: 批評 3 章「読み筋」）。開発の道具として先に作れる点を重く見て、上位に置いた
- 規模: S〜M

### 絵巻起こし
- 種別: 拡張
- 領域: presentation
- 一言: ランが終わると、その道のりを横長の絵巻 1 枚に描き起こし、画像として保存・共有できる。スコアは描かない。
- 仕組み:
  - 死亡・踏破・離脱のたびに、1 枚の横長の画像（例 1920×540）を組む
  - 左から: 階ごとの小さな縮図（章の様式の色）→ 倒した章ボス → 第三の顔が借りた技 → 仇 → 最後の相手
  - 下の帯: その回の紋（`ui/crest.ts` の系統の帯と珠）・主に使った型
  - **縮図は降階の時点で描画側が 1 枚取って持つ**（描画の中だけで完結し、state に書かない）。終わってから作り直さない
  - 踏破の回だけ、題字の墨書きと落款（seed から座標ハッシュの作法で決まる朱印の形）が入る
  - 保存はファイルとクリップボード。Electron なら Steam のスクリーンショットへも送る
- なぜこのゲームで: 単一指標を出さない原則の下で「このランはどうだったか」を語る答え（S5 問 3）。保留中の案 B「絵巻」（title-ideas 3 章）の行き先。紋がすでにビルドを絵にしている
- 着想元: Balatro の最後の手札のスクリーンショット、Slay the Spire のラン履歴。点数を貼る文化から、道のりを貼る文化へ
- 安っぽくならないための要点 / リスク:
  - 文字で集計を並べない（「撃破 1,204」の行は無し）。絵が語る
  - 縮図の保持は 21 階 + 深みで枚数が増える。章ごとに 1 枚へ間引くなど上限を決める
- 議論で変わった点: 縮図を降階の時点で取る形にした（批評の補足）。種銘は入力手段が無いので外した
- 規模: M

### 一章体験
- 種別: 新要素
- 領域: platform
- 一言: 体験版は「章 1 の 5 階 + 作り直したスライム王 + 門前町の一部」。初陣で教え、スライム王で試し、章 2 の顔を覗かせて終える 1 時間の弧にする。
- 仕組み:
  - 範囲: ジョブ 3（近接・遠距離・術を 1 本ずつ）、型 5〜6、祝福 4 系譜、依頼 6。見せない層（誓約・残響・改鋳・深み）を最初に決める
  - **スライム王を「試金の主」に作り直す**（批評の派生案「試金主」を取り込み）。今の 3 段階（跳躍 → 呑み込み → 膨張）に、段階ごとに 1 つの読みを当てる
    - 跳躍: 着地の予告の黄が長く、黄の間に潜って殴れば落下を止められる
    - 呑み込み: 吸い込みは赤のコミット。受け流すと吐き出されて即ダウン。避けるより返す方が速い
    - 膨張: 分裂体が陣を組み、中の 1 体が大将。大将を先に割ると分裂体が敗走し、段階が一気に進む（群勢・敗走の既存の仕組み `system/jinFormations.ts` に乗せる）
  - 倒すと章 2 の休符（地下 6 階）へ降り、地下寺院の景色と「この章の主」の予習だけを見せて終わる。終わりの画面は絵巻起こしと、ほしいものリストへのボタン
  - **引き継ぐのは記録だけ**: 図鑑（見た・倒した）と来歴の記録（名を付けた遺物の名前と逸話）を製品版へ移す。倉庫は引き継がない。記録だけなら保存の形が変わっても移せる
  - 解放の速さは体験版だけ変えない。製品版の開帳を先に良くして、同じ値で出す
  - 公開は Next Fest の 1 か月以上前
- なぜこのゲームで: 章の弧（休符 → 登り → 章ボス）がすでにあり、章 1 が自然に 1 本の弧になる。章ボスの「行為で進む段階」は盗賊王・油壺の王・鏡の騎士で 0%（S2）なので、最初の章ボスで「行為で進める」を確実に体験させないと、後の章ボスの設計が読まれないまま終わる。教える（初陣）→ 試す（試金の主）→ 欲しがる（章 2 の顔）が、戦闘の言葉で閉じる
- 着想元: Next Fest の上位作の体験版の長さと「弧のある体験版」の転換率。Hollow Knight の偽りの騎士・Celeste の章の終わり（覚えた動きの試験）。試すのが動きでなく「読み」である点を変えた
- 安っぽくならないための要点 / リスク:
  - 体験版を「機能を削った物」に見せない。章 1 を完結した弧として作る
  - 「体験版の遺物を製品版へ」は約束しない（旧データの互換を作らない方針と、`REPLAY_VERSION` 35 の速さで破れる）
  - Steam Cloud は appid ごとに別。ローカルの `%APPDATA%` は共有できるが、クラウドを使う人の引き継ぎは手で移す手順が要る
  - スライム王の作り直しは `core/replay.test.ts` と `qa:probe -- --bosses` の更新を伴う
- 議論で変わった点: 保存の引き継ぎを「記録だけ」に縮め、体験版だけの解放の速さをやめた。批評の派生案「試金主」をこの案の終わりの相手として統合した
- 規模: L

### 開帳
- 種別: 拡張
- 領域: meta
- 一言: 型・祝福の系譜・刻印符の族を、時間でなく「その型を遊ぶのに要る腕を 1 ランの中で見せた時」に開く。開いた物は門前町の御開帳として見せる。
- 仕組み:
  - 型ごとに「前提の手」を決める。条件は **1 ランの中で** その手を N 回（累計にしない）
    - 例: 剣で応手を 10 回 → 盾（受け溜め）が開く
    - 見切り 5 回 → 長銃（止まって狙う勇気は、避けられる人だけが持てる）
    - 1 撃で 3 体以上に当てる 20 回 → 鎖
  - 材料は既存のラン中の数え（`meta/quests.ts` の `QuestCounters` の `counters`・`justDodges`・`staggers`・`bursts`・`reactions` など）。足りない手（応手・多段の当て）は `QuestCounters` に 1〜2 項目足す
  - 判定はラン終了時に `recordQuest` と同じ場所で行い、開いたかどうかだけを既存の解放の保存に足す。`UnlockCondition` に `{ kind: "deed"; deed; count }` の形を 1 つ足す
  - 開いた物は、次に拠点へ戻った時、門前町の該当の建物で見せる（武器小屋に新しい型が掛かる、社に新しい系譜の幟が立つ）。2 秒以内・飛ばせる。見せたかは `ui/seen.ts`
  - 開帳した物は稽古場ですぐ試せる
- なぜこのゲームで:
  - 拠点は強さを増やさない（`hub-design.md`）。開帳が配るのは強さでなく選択肢の種類
  - 開く順が「その型を遊ぶために要る腕の順」になり、カリキュラムを兼ねる。開いた時にはその型を遊ぶ腕があるので、10 時間後に全部が開いても溺れない（批評の問 7）
  - 門前町は寺社の町で、「御開帳」が世界観の語としてそのまま立つ
- 着想元: Ball x Pit の小出し、Hades の武器の鍵。数値の強化を抜き、「時間で配る」も抜いて、「手で開く」に変えた
- 安っぽくならないための要点 / リスク:
  - 条件を累計にすると作業になる。1 ランの中で、その手を自然に重ねた時だけ開く
  - 条件が厳しすぎて開かない人が出る。目安は 1 ラン目で 1〜2、5 ランで型の半分。届かない人のために、同じ型の前提を複数（どちらか 1 つ）にする
  - 熟練者向けの「全部開く」の設定はユーザーに聞く
- 議論で変わった点: 「時間で配る」を捨て、批評の「覚えた動詞で開く」を採った。依頼が 1 ランぶんしか数えない作りに合わせ、条件を「1 ランの中で N 回」にして保存キーを増やさない形にした。「暦」が時間の配りを示すので名前から外した
- 規模: M

### 手合
- 種別: 新要素
- 領域: run
- 一言: 毎日 1 つ、決まった局面（場・相手・型）で 1 回だけ立ち合う 2〜4 分の勝負。Steam のリーダーボードに時間だけを並べ、上位の棋譜をゲームの中で再生して学べる。
- 仕組み:
  - 局面は手で作った 30 日分の表を回す。場は主の間の格子 1 つ、相手は陣 1 つか章ボス 1 体（段階の途中からも可）、型は武器 1 本。祝福・装備・スキル石は持ち込まない
  - 例: 「鎖の型で、大将付きの鶴翼の陣」「盾の型で、盗賊王の第 2 段階から」
  - 挑めるのは 1 日 1 回。稽古場で同じ局面を何度でも練習できるが、記録には載らない
  - **棋譜棚**: リーダーボードの各行に、入力列のリプレイを UGC として添える（自前のサーバを持たない）。並べる値は「討ち取りまでの時間」だけ。被弾 0 は「無傷」の印として行に添え、2 つ目の数字にしない
  - 2〜4 分なので、見る側の端末で上位 10 本を再シミュして、結果の一致した物だけを表に出せる
  - ボードの名前に版を含めて切る（`teai-2026-10-02-v35` の形）。古い棋譜は「この版で再生できる」の注記にとどめる
  - 再生では「読み筋」を入れられる。上位の人が赤の何フレーム目で返したかが見える
- なぜこのゲームで:
  - ボスは乱数で技を選ばず、プレイヤーを読む（`pickMove`）。乱数の揺れが無いので、上位との差は純粋に読みと手順の差で、棋譜はそのまま教材になる
  - 型ごとに戦意の曲線が違うので、日替わりの型が「今日の課題」になる。免状の奥伝の練習の場も兼ねる
  - 全 21 階のランを並べないので、単一の並びの例外を最小にできる
- 着想元: 詰将棋（決まった局面で最短の手順）、格闘ゲームのトレーニングの課題、Spelunky のデイリー。ローグライクのデイリーの定番「1 ラン全部を競う」を、最も腕が見える 1 戦に縮めた
- 安っぽくならないための要点 / リスク:
  - 単一の並びは原則の例外。「手合だけ並べる。深みも今日の挑戦も並べない」を `DESIGN_PRINCIPLES.md` に書く前に、ユーザーの確認が要る
  - ボスラッシュ・アリーナの定番に見せない。「1 日 1 回の本番」と「稽古場の練習」の区別を崩さない
  - steamworks.js のリーダーボード・UGC の対応は要確認。無ければ native の口を足す必要があり、出店支度が重くなる
  - 環境をまたぐ決定性（目安箱で確かめる）が崩れていたら、見る側の再シミュが一致しない
- 議論で変わった点: 元の「棋譜棚」（全ランを並べる）を、批評の派生案「手合」（出典: 批評 3 章）へ統合した。全ランの棋譜は記録の蔵の中だけで扱う。並べる値を時間 1 つにし、版でボードを切る形にした
- 規模: L（出店支度の上で）

### 免状
- 種別: 拡張
- 領域: meta
- 一言: 実績を「型ごとの中伝・奥伝」に組み直す。数え上げでなく「その型の要を 1 回やった」を、Steam の実績として残す。
- 仕組み:
  - 15 の型それぞれに 2 段（計 30）
    - 中伝: その型を選ぶ理由そのものを 1 回。例: 長銃 = 狙いが満ちた一発で大将を討つ / 盾 = 受け溜めの放出で章ボスを怯ませる / 短銃 = 強装填のまま 1 つの陣を崩す
    - 奥伝: 章ボスの段階を、その型の要で進める（例: 盾 = 受け溜めの放出で章ボスを段階ごとダウンさせる）
  - 配線は 2 段: ラン中は `QuestCounters` に型の要の項目を足して数え、ラン終了時に達成を履歴に残す。実績（`meta/achievements.ts`）は履歴を読むだけ。`achievements.ts` に状態を足さない
  - 報酬は見た目だけ（武器掛けの房・紋の縁）
  - 数え上げの実績（百の屍など）は 10 前後に減らす
  - 奥伝は bot が 0% で QA で確かめられないので、各型 1 回、人が成立を確かめる手順を `docs/` に置く
- なぜこのゲームで: 戦意 15 通りを初見にどう伝えるか（S1 問 4）への、UI に説明を書かない答え。免状の名前と条件が、その型の遊び方の手引きを兼ねる。Steam の全体の達成率（「盾の奥伝 0.8%」）が配信で語られる材料になる
- 着想元: Dead Cells・Hades の武器ごとの実績、武術の免許の段。「通算で何体」でなく「要を 1 回」を残す形に変えた
- 安っぽくならないための要点 / リスク:
  - 条件が細かすぎると作業になる。中伝は「その型を選ぶ理由」に限る
  - 「免許皆伝」は目覚めのラベルで使用済み。「皆伝」の語は使わない
- 議論で変わった点: 初伝（放出は振りの開始で自動的に起きるので、数え上げと変わらない）を削って 2 段にした。依頼の数えを流用し、履歴を経て実績へ渡す配線を明記した
- 規模: M

### 濃淡予告
- 種別: 改善
- 領域: presentation
- 一言: 予告の黄と赤を、色だけでなく「縁だけ / 中まで濃く塗る」の墨の濃淡でも描き分け、赤へ変わる瞬間の音は自分に最も早く当たる 1 体だけで鳴らす。
- 仕組み:
  - 黄（まだ割り込める）: 薄墨の縁だけ。中は塗らない
  - 赤（コミット）: 濃墨で中まで塗り、縁が内へ滲む
  - 破線は使わない（`render/skillHud.ts` の `DELAY_DASH` が自分の遅延スキルの意味で使っている）
  - 赤への変わり目の音（筆を置く「トン」）は、「自分を狙っている敵」のうち「画面内で最も早く当たる 1 体」だけ鳴らす。陣の 6〜10 体が同時にコミットしても 1 回
  - 先に、スプライトの赤の染め（`renderer.ts` の `COLOR_TELEGRAPH`）と線の `TELEGRAPH.commitColor` を 1 つの定数へまとめる。そのうえで設定に色の組み（黄 / 赤・青 / 朱・白 / 墨）を置く。濃淡は常に効く
- なぜこのゲームで: 予告は約束の芯で、ストアの縮小された GIF で読めないと口上が伝わらない。危険の度合いを墨の濃さで示す文法は、墨淵という名前と直結し、「墨」を仕組みの言葉にする（S6 問 2）最初の一歩
- 着想元: Steam の 2025 年のアクセシビリティの項目（代わりの色）。Celeste の支援の設定。色の差し替えで終えず、世界観の文法に変えた
- 安っぽくならないための要点 / リスク:
  - 暗がり・反転層の紫・深みの色相の回転と重ねて読めるかを `map:shot` で確かめる
  - 塗りが画面を汚さない濃さにする（陣の全員が赤の瞬間に床が見えなくならない）
- 議論で変わった点: 破線を捨てて塗りの差にした。音を 1 体に絞った。色の定数の二重を先に解く手順を足した
- 規模: M

### 旗倒れ
- 種別: 拡張
- 領域: presentation
- 一言: 大将の背に陣形の紋の旗指物を立て、大将を討った瞬間に旗が倒れて陣が一斉に背を向ける絵で見せる。他のアクションローグに無い「陣が崩れる」を決め絵にする。
- 仕組み:
  - 大将の今の印（`render/jinUi.ts` の頭上の小さな三角 `LEADER_MARK_*`）を、陣形ごとの紋の旗指物に置き換える。旗は遠くから見え、ミニマップにも小さく出る
  - 大将を討つか群勢が尽きると: 旗が倒れる → 陣の中心から墨の波紋 → 全員が同じフレームで背を向ける。1 秒以内
  - スローもヒットストップも足さない（ヒットストップはすでに 1 対 1 で 20〜35% と目標を超えている）。絵と音だけで見せる
  - 逃げる敵を追うか見逃すかの判断は今の仕組みのまま
- なぜこのゲームで: 陣・群勢・敗走は他の見下ろしアクションにほぼ無い単位（S2・S7 の強み）で、それが絵になっていないのは看板の損。旗が遠くから見えると「どの陣を崩すか」を選ぶ情報になり、陣の 6 割が素通りされる問題（S2）の手がかりにもなる
- 着想元: 戦国の合戦絵巻、Total War の総崩れ、Mount & Blade の敗走。大軍の戦略の絵を、1 人のアクションの手応えに縮めた
- 安っぽくならないための要点 / リスク:
  - 旗の紋は陣形の数だけ描く（ドット絵の Agent の仕事）。紋の判別が 480×270 で付くかを先に試す
  - 毎回の演出を長くしない
- 議論で変わった点: 実装済みの祝福「総崩れ」と衝突するので改名。スローをやめた（批評の指摘）
- 規模: M

### 撮影台
- 種別: 基盤
- 領域: platform
- 一言: リプレイを HUD なし・自由なカメラ・スロー・こま送りで再生し、1920×1080 の連番画像に書き出す。まず開発用の道具として作り、後で終わりの画面の「見得」の書き出しへ広げる。
- 仕組み:
  - **段 1（開発用）**: `tools/map-shot.html` と同じく、Playwright で Chromium を回す `npm run` の 1 本。リプレイと「開始・終了のフレーム」「カメラ（追従・固定・ゆっくり寄る）」「速度」を渡すと PNG の連番を出す
    - 内部の描画は 480×270 の 4 倍（`RENDER_SCALE`）で、ちょうど 1920×1080。拡大の滲みが無い
    - カメラは `state.camera` を描画側で上書きする（state は触らない）
    - 同じ場面を何度でも同じに撮れるので、トレーラーの編集で「あと 3 フレーム早く」が効く
  - **段 2（プレイヤー向けの見得）**: ラン中の「上手さが見える 3 秒」を、終わりの画面に最大 3 つ並べ、選ぶと同じ経路で書き出す（批評の派生案「見得帳」を取り込み）。見得の候補は既存の判定（`system/moments.ts` の共通の瞬間・応手）から拾う。例: 赤の予告を受け流して 2 秒以内に処刑 / 旗倒れ / 反応の連鎖で 5 体以上。1 ランで同じ種類は 1 つまで
- なぜこのゲームで: 決定性と描画の分離（不変条件 1・2）がそろっているので、撮影のための特別な経路が要らない。個人開発では、トレーラーの撮り直しの費用が最も重い。見得は「読みが成功した瞬間」なので、切り抜きそのものが口上の宣伝になる
- 着想元: レースゲームのリプレイの撮影モード。Overwatch の Play of the Game が「点数の高い瞬間」を選ぶのに対し、「読みが成功した瞬間」を選ぶ。歌舞伎の見得
- 安っぽくならないための要点 / リスク:
  - 見得に「すごい！」の文字や点数を出さない。終わりの画面に静かに並ぶだけ
  - トレーラーの音（批評の問 6）: 合成の音楽がトレーラーの水準に届くかは別の問い。段 1 の書き出しは画だけにし、音はトレーラーの編集で決める
  - 見得の名前は GLOSSARY で決める
- 議論で変わった点: まず開発用に絞って規模を下げ（批評の補足）、批評の派生案「見得帳」を段 2 として統合した
- 規模: S（段 1）+ M（段 2）

### 訳語台帳
- 種別: 基盤
- 領域: platform
- 一言: 表示の文字列を 1 つの表へ集め、英語の訳し方の原則と、簡体字の字形を発売の前に決める。まず「新しい表示文字列は表に足す」を今日から作法にする。
- 仕組み:
  - **段 0（今すぐ）**: 並行の実装が毎日新しい直書きを増やしている。`docs/AI_WORKFLOW.md` とレシピに「新しい表示文字列は表に足す」を入れ、増える分を止める。既存の移行は後から画面ごと
  - 段 1: 表示の文字列を key 付きの表へ移す。`menuBudget.test.ts` の画面ごとの予算を、英語の幅（日本語の 1.5〜2 倍）でも数えるテストを同時に足す
  - 段 2: 英語の命名の原則。世界観の固有名はローマ字 + 意訳の 2 段で 10〜15 語だけ残し（Bokuen・Jin・Ougi など）、それ以外は 2 語までの英語に意訳する。漢字 1 字のアイコンは英語圏では「印章」として見た目の個性になる
  - 段 3: 字形。UI の文字は `render/pixelText.ts` の 1 か所を通る（不変条件 5）ので、言語に応じた字形の切り替えはここだけで済む。簡体字は OFL のドット字形（収録とライセンスは要確認）
  - 順序: EA は日本語 + 英語。1.0 で簡体字
- なぜこのゲームで: 熟語で名付ける原則（GLOSSARY）は英語では文になりやすい。仕組みの説明を Tips ノートに集めた方針は、訳す量を 1 か所に集めている。Steam の利用者は英語と簡体字で 6 割を超える
- 着想元: Silksong の簡体字の訳の質で叩かれた事例。量より訳の質を先に設計する
- 安っぽくならないための要点 / リスク: 機械翻訳のまま出さない。固有名に残す語の選定はユーザーが決める
- 議論で変わった点: 時期を前倒しし、段 0（作法で増加を止める）と英語の幅の予算テストを足した
- 規模: XL（段 0 は S）

### 出店支度
- 種別: 基盤
- 領域: platform
- 一言: Steamworks（実績・クラウド・Rich Presence・リーダーボード）を main プロセスにだけ配線し、step からは一切見えない形にする。
- 仕組み:
  - `electron-design.md` 4.5 の想定どおり、Steam の native module を main に置く。renderer とは preload の IPC で 4 つだけ話す（実績を解く / Rich Presence を書く / リーダーボードへ送る・取る / UGC を添える）。ブラウザ版では同じ口を空の実装にする
  - 実績は履歴から導いた結果を、ランの外で送るだけ。**実績の表は `achievements.ts` を正にし、Steamworks の管理画面へ流し込む書き出しを 1 本作る**（二重管理を避ける）
  - Rich Presence は Steamworks の「言語ごとの文の表」にトークンと変数だけを送る作法。表示文（「地下 12 階・廃城・盗賊王に挑む」）は訳語台帳と同じ表から作る
  - クラウドは Auto-Cloud（`WinAppDataRoaming/BOKUEN/save/*.json`）で今の構成のまま
- なぜこのゲームで: 永続化の 1 つの入口（不変条件 8）と、step が外界を読まない規律（不変条件 3）があるので、Steam は外側に付け足すだけで済む
- 着想元: Electron 製インディーの steamworks.js での対応
- 安っぽくならないための要点 / リスク:
  - native module で Electron の版の上げ下げが縛られる。fuses・`app://` との相性を先に確かめる
  - 実績のアイコン 64×64 の絵が要る（免状と合わせて描く）
- 議論で変わった点: Rich Presence の作法と、実績の表の書き出しを補った
- 規模: L

### 栞
- 種別: 新要素
- 領域: run
- 一言: 降階の確認の場面でだけ「栞を挟んで退く」を選べ、次に起動した時その階の頭から続けられる。続けると栞は消える。
- 仕組み:
  - **自動では残さない**。階段の降階の確認で「栞を挟んで退く」を選んだ時だけ書き、ゲームを終える
  - 階の途中の強制終了は、今と同じく「離脱」として履歴に入る。危なくなったら落として階の頭からやり直す悪用を、これで塞ぐ
  - 作り直しは、降階の直後の状態の直列化を本命にする（階は `buildFloor` が rng から作り直せるので、持つのはプレイヤー・ビルド・rng の状態）。入力列の再シミュは、深みに上限が無いので使わない
  - 栞から続けたランも、リプレイは「栞の前」と「栞の後」の 2 本をつないだ物として残す（決定性のテストは直列化の往復で固定する）
- なぜこのゲームで: ランは 50〜70 分、深みは際限が無い。Steam Deck と短い遊びの人は中断が無いと始めない。手合（2〜4 分）と合わせて、短く遊びたい人の入口が 2 つになる
- 着想元: Hades の部屋の間での中断、Dead Cells の中断のセーブ。「降階の確認でだけ、自分の意思で挟む」に限った
- 安っぽくならないための要点 / リスク:
  - **ユーザーの決定「中断セーブ（続きから）は作らない」（`title-ideas.md` 2 章）の見直しを求める案**。Steam の発売を目標にした今、再考を問う形で出す
  - 状態の直列化は、state の型が増えるたびに追随が要る。直列化の往復テスト（作る → 直す → 同じ結果）を必ず持つ
- 議論で変わった点: 自動の栞をやめ、降階の確認での手動だけにして悪用の穴を塞いだ。作り直しを再シミュでなく状態の直列化に決めた
- 規模: L

## 捨てた案と理由

| 案 | 扱い | 理由 |
| --- | --- | --- |
| 棋譜棚（全ランのリーダーボード） | 手合へ統合 | 50〜70 分のランは見る側の再シミュが重く、単一の並びの例外が広がる。並べるのは手合だけにし、全ランの棋譜は記録の蔵の中で扱う |
| 墨跡（他人が倒れた場所の染み） | 手合の後に再提案 | 全ランの棚を捨てたので土台が無い。批評の「リーダーボードの details に位置を詰める」「崩せば弔いの選択肢が増える」は良く、全ランの共有を作る日に戻す |
| 種銘（読める seed） | 捨てる | Electron 版に seed の入力手段が無く、漢字はゲーム内で打てない。並べる場は手合（手で作った表）に絞ったので、口で言える seed の価値が下がった |
| 開帳の暦（時間で配る） | 開帳へ改める | 時間で配ると「上手い人ほど早く開く」が消え、10 時間後に同じ溺れが来る（批評） |
| 普請の道（EA の範囲・値段・ゲーム内の縄張り） | 案から外し、ユーザーへの問いへ | 範囲・値段・EA にするかはゲームの案でなくユーザーの判断。ゲーム内の縄張りで予定を見せると、更新が遅れた時に空き地が約束の破れの記念碑になる（批評）。「EA は 4 章 + 最深の主 + 踏破、深みは試しの層」「日付でなく順を約束」は HANDOFF の問いとして残す |
| 試金主（スライム王の作り直し） | 一章体験へ統合 | 体験版の終わりの相手として、教える → 試す → 欲しがるの弧の中で語る方が強い |
| 見得帳 | 撮影台の段 2 へ統合 | 書き出しの経路が撮影台と同じ |
| 総崩れ（名前） | 旗倒れへ改名 | 実装済みの結びの祝福と衝突 |
| 看板一句（名前） | 口上へ改名 | 「看板」は拠点の飾り（称号の看板）で使用済み |
| 免状の初伝 | 削る | 放出は振りの開始で自動的に起きるので、数え上げと変わらない |
| 体験版の遺物を製品版へ引き継ぐ | 削る | 旧データの互換を作らない方針と、版の速さで破れる約束になる |
