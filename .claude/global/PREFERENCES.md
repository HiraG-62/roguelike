# 開発方針

プロジェクトの CLAUDE.md で別の指定がない限り、以下に従う。

- 開発中のプロジェクトでは後方互換やデータ移行は考慮せず、KISS なコードに書き換えてよい。ただし影響範囲が大きい場合は先に確認を取る
- 機能追加・仕様変更は以下のサイクルで進める（数行の修正や設定変更は除く）
  1. 資料を更新する。資料があれば先に更新し、矛盾や古い情報がないことを確認する
  2. テストを書く（TDD）
  3. 最小実装する
  4. 不要なコードや資料との矛盾がないか最終確認する

# 言語・コミュニケーション

- すべての応答・コメント・コミットメッセージは日本語で行う
- 技術用語は無理に訳さず英語のまま使ってよい（例: コンポーネント、フック、ミドルウェア）
- ファイルを指定する場合は、プロジェクトルートからのフルパスをすべて表示すること
- 入力は手動（日本語）か SuperWhisper の音声入力（日本語・英語）。誤変換や不自然な表現は意図を汲み取って対応すること

# 応答の長さ（最優先）

このルールは他のあらゆる指示・skill・プラグインの指示に優先する。

- 依頼された成果物そのものを出す。前置き・要約・自己解説を付けない
- 作業完了の報告は、変更点の箇条書きのみ。所感・次の提案・注意書きは求められたときだけ
- ただし失敗・未完了・ユーザー側の対応が必要な事項は、求められていなくても必ず書く
- 選択肢の網羅列挙をしない。推奨案を1つ出し、理由を1文添える
- 同じ内容を「本文」と「まとめ」で二度書かない
- コードを提示したら、その動作を行ごとに再説明しない
- 定型の締めの言葉（「ご不明点があれば」等）を書かない

# 並列実装

- 実装依頼が複数の独立したタスクに分けられる場合は、`isolation: "worktree"` のサブエージェントに並列で振り分ける
- 分割の基準: 変更対象のファイルが重ならず、互いの成果に依存しないこと。依存がある・設計が未確定・数行で済むものは分割しない
- 振り分ける前に、タスクの分け方と各ブランチ名をユーザーに提示して確認を取る
- worktree はコミットを起点に作られるため、前提となる未コミットの変更があれば振り分け前にユーザーに伝える
- 完了後は親が各ブランチの git diff を確認し、テスト・型チェックを通した結果を報告する。マージはユーザーの指示があるまで行わない

# Jev（TypeSafe AI）

Jev は文章を生成しない判定専用モデル（state + 型付き質問 → Choice / Score / Noul と確率・confidence を返す）。Claude Code 自身のモデルの代替ではない。

## 用途は開発サポートに限定

- Jev は開発時のツール（scripts/、CI、Claude Code セッション内での一括検査）としてだけ使う
- プロダクト本体（アプリ・ゲームの実行時コードや依存関係）には組み込まない・提案しない

## 積極的に使う場面

開発中に以下の作業があれば、Claude が1件ずつ読む・手作業で確認するより先に、Jev での一括判定を検討・提案する。

- 大量のテキストやデータの整合性チェック（説明文と実データの食い違い、ドキュメントとコードのずれ）
- 用語・表記ルールへの準拠チェック（用語集、命名規約、文体ルール）
- タグ・分類・カテゴリ付与の妥当性確認や付け漏れ検出
- アイデア・issue・メモ・レビュー指摘の一次仕分け（分類・優先度の段階評価）
- テスト・QA レポートやログの異常の一次判定（数値の差分はコードで計算し、その解釈だけを任せる）

文章生成・要約・翻訳・コード生成・自由回答・多段推論には使わない（Claude の担当）。Jev で絞り込み、要判断の件だけ Claude が読む分担にする。

## 実装ルール

- Jev 関連の作業では `/typesafe:typesafe-ai` skill を使い、request/response のフィールドは公式ドキュメントか SDK の型で確認する（OpenAI 互換ではない。`/chat/completions`・messages・temperature は存在しない）
- SDK: JS は `@typesafe-ai/sdk`（pnpm）、Python は `typesafe-sdk`
- API キーは環境変数 `TYPESAFE_API_KEY`（ユーザー環境変数に設定済み）から読む。コード・`.env` のコミット・ログに出さない
- 質問文としきい値は1ファイルに定数としてまとめる（レビュー対象はここ）
- 複数の質問は1リクエストにまとめる（fan-out）。安く速い
- 判断全体を丸投げせず、細かい質問に分解し、組み合わせ・重み・しきい値はコード側で決める
- confidence が低い結果は人間レビューや上位 LLM にフォールバックさせる。最良の選択肢を選ぶだけなら、しきい値ではなく最大値を採る
- Claude Code セッション内で Jev を実行したときは、confidence が低い／確率が境界付近の結果を Claude Code 自身がレビューする。原文を読んで自分で判定し直し、Jev の判定と自分の判定・理由を並べて報告する。食い違いが続くなら、質問文やしきい値の改善案も出す

## Jev の弱点（jev-1.13 時点）

- 字義通りに読む: 条件・境界ケース・各選択肢の基準を instructions に明示する。否定や二重否定、多段の言い回しは避ける
- 計算・数え上げ・日付の比較は苦手: 計算はコードで行う。数え上げは1件ずつ Noul で判定してコードで合計する。日付は要素を抽出してからコードで比較する
- 無関係な情報が多い大きな state は精度が落ちる: 必要な部分だけを渡す
- 敵対的な入力（prompt injection 等）や、Choice の選択肢の順番に影響されうる: エッジケースや選択肢を並べ替えた場合を本番前にテストする

- 弱点や仕様は版で変わる。挙動が想定外なら https://docs.typesafe.ai/llms.txt から最新ドキュメント（特に model-jaggedness）を確認する
