# QA シミュレーション結果

ヘッドレス自動プレイ（`src/qa/bot.ts` のヒューリスティック bot）による長時間シミュレーションの結果。
`SIM_FULL=1 npx vitest run src/qa/simulation.test.ts` で生成。

- 実行: 30 seed（50000〜50029） × 装備 3 パターン（empty / rareLoadout / uniqueLoadout） × 60,000 ステップ（≒1000 秒）= 90 run
- 生成日時: 2026-09-22T21:30:29.461Z（このリポジトリ上での実測値。以後のコード変更で数値は変わり得る）
- bot について: 最寄りの交戦中の敵に照準して距離に応じ近接/射撃、windup・strike を検知したら 70% の確率で逆方向にダッシュ回避（30% は「人間らしい」見逃し）、敵がいなければタイルグリッド上の BFS 経路で未クリア部屋 → 階段の順に移動する。パーフェクトプレイはしないため、死亡率や到達 depth は「人間の上手いプレイヤー」の指標ではなく、あくまで一定水準の自動プレイでの相対比較（装備差・キーストーン差・depth 別難度）として読むこと。

## 1. 例外

90 run すべてで例外は 0 件。

## 2. 不変条件違反（NaN / 壁めり込み / floorItems id 重複）

NaN 混入・floorItems の id 重複は 0 件。壁めり込みは 90 run 中 18 run（20%）で検出されたが、調査の結果すべて次の 2 パターンに分類できた。

### 2-1. wisp の壁抜け（バグではない）

`wisp`（`src/data/enemies.ts` の `phasing: true`）は仕様上「壁をすり抜けて移動する」敵なので、`overlapsWall` が true になるのは意図通り。QA 側の判定 (`src/qa/simulation.test.ts` の `anyEnemyInWall`) では `phasing` な敵を除外して数えている。

### 2-2. ドアタイル上でロックされた敵が「壁の中」判定になる（軽微な不整合、要確認）

上記を除外しても 18 run で発生。以下の条件で固定再現できた。

- **再現手順**: seed=50000, 装備プロフィール=uniqueLoadout（`SLOTS` 全部位を itemLevel 20 / rarityBoost 25 で unique 抽選、無ければ引けた最高レア度）、bot 操作でプレイし続ける
- **発生タイミング**: ステップ 27431（`state.tick`=25329, `state.depth`=5）
- **現象**: `knight`（id=2865, elite="hasted", phase="windup", roomIndex=4）が部屋の **ドアタイル** の上に立っている瞬間に、プレイヤーが部屋の内側に入り `lockRoom`（`src/system/floor.ts`）が呼ばれた。ロックによりそのドアタイルが `state.lockedTiles` に追加される。`isSolidTile`（`src/system/physics.ts`）は「壁タイル (`Tile.Wall`)」と「ロック中のタイル」を区別せずどちらも solid 扱いにするため、たまたまドアタイル上にいた敵はその瞬間から `overlapsWall` 的には壁に埋まった扱いになる。
- **影響の推測**: 見た目のグラフィック破綻や即死は確認していない。ただし `moveEnemy`/`moveBody` は現在位置ではなく移動先候補だけを `overlapsWall` で判定するため、この状態になった敵がその後ちょうどこのタイル付近に留まろうとする移動（`separate` によるノックバック等）を試みた場合に動けなくなる可能性がある。プレイヤー自身は `enterMargin` / `ENTER_PROBES`（`insideRoom`）でドアを跨いでいる間はロックされない配慮があるが、敵の側には同様の配慮がない非対称性がある。
- **頻度**: 90 run 中 18 run（20%）。empty プロフィールでは到達 depth が浅く部屋数を稼げないためか発生 2 件のみ、rareLoadout / uniqueLoadout（深く進みやすい）で計 16 件と多い。

この 2-2 は今回のタスクの所有ファイル外（`src/system/physics.ts` / `src/system/floor.ts`）のため修正はしていない。バグとして扱うか仕様内の許容範囲とするかはチームの判断を仰ぎたい。

## 8. バランス所見

- **depth 2 が最大のボトルネック**: 死亡の半数（44/87 件）が depth 2 で発生している。特に knight・slime・bomber・eye が絡む死亡が集中しており、depth 2 での敵密度・種類構成が急に厳しくなっている可能性がある。
- **死因の主役は Reaper**: 全死亡の 64% に Reaper が絡む。bot はフロアクリアに時間がかかるほど Reaper の追跡から逃げ切れず倒れており、探索・戦闘の遅さがそのまま Reaper 落ちに直結する設計になっている。
- **装備差は到達depthにはっきり出ている**: 素手 1.97 → rare 3.20 → unique 4.03 と、素手を除けば装備の強さに応じて素直に伸びている。killsやbest comboも装備が強いほど大きく伸びており（69.5→165.5→236.6 kills, 26.0→38.9→79.2 combo）、レアリティによる強化は機能している。
- **キーストーンはこの bot のプレイでは概ねプラス**: 事故死を増やしている様子はなく、むしろ生存に寄与している（4章）。
- **unique のラン中ドロップがほぼゼロ**: 7章の通り、ラン中に unique を拾う体験が実質発生していない。意図的な渋さなら問題ないが、「ラン中にunique装備を更新する」体験を用意したい場合はドロップ率の見直しが要る。
- **パフォーマンスは全く問題ない**: 平均 0.03ms/step で 60fps 予算に対して余裕。

## 9. 提案

1. **depth 2 の難度カーブを緩和する**: 死亡の半数が集中している。`enemiesPerDepth` / `depthHpScale`（`src/data/enemies.ts`）や depth 2 で解禁される敵構成を見直し、depth 1→2 の難度ジャンプを緩やかにする。
2. **Reaper 絡みの死亡が多い点への対処**: `REAPER.appearAfter` / `warnAfter`（`src/data/tuning.ts` 系）の猶予秒数を、平均フロア滞在秒（6章: depth 3 以降は 100 秒超）と突き合わせて再調整するか、Reaper の速度・被弾時のノックバックで振り切りやすくする調整を検討する。
3. **ラン中の unique ドロップ率を見直す**: 90 run・アイテム 1226 個のドロップ中 unique が 0 個だった（7章）。`rarityBoostPerDepth` や部屋クリア/depth到達ボーナスの `rarityBoost` を上げるか、一定 depth 到達後は unique の重みを底上げする救済を検討する。
4. **ドアタイルの `lockedTiles` 判定を敵にも配慮する**: 2-2 で見つけた「敵がドアタイル上でロックされると壁の中判定になる」問題。プレイヤー向けの `enterMargin`/`insideRoom` のような猶予を敵の位置にも適用するか、影響が無視できるなら「許容する既知の挙動」としてコメントを残すことを検討する。
5. **QA bot 自体の限界を踏まえた継続計測**: 今回の bot は windup/strike 検知からの回避に 30% の意図的な失敗率を入れているため、死亡率が高め（93〜100%）に出る。今後バランス調整をしたら同じ bot・同じ seed set で再計測し、死亡率や到達depthの変化を差分で見るのが良い（絶対値よりトレンドが有用）。
