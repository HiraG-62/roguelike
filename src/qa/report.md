## 提案

1. depth 2 前後の敵密度・HPスケーリング（enemiesPerDepth / depthHpScale）を見直し、難度の急上昇を緩和する。
2. 死因トップの敵（boar）の windup 時間や被弾判定の猶予を見直し、回避余地を増やす。
3. rare / unique 装備の有無で到達depthに大きな差が出ていない場合、レアアフィックスの倍率調整でビルドの手応えを強める。
4. キーストーンつき装備が事故死を増やしている場合は、リスクに見合ったリターン（回復・被ダメ軽減の代替経路）を補強する。
5. Reaper 出現後に倒しきれず時間切れで死ぬケースが目立つ場合は、warnAfter / appearAfter の猶予時間を調整する。

## 調査メモ（引き継ぎ）

### 「同時攻撃の上限超過」はメトリクス側の数え方の差で、ゲームロジックのバグではない可能性が高い

- 現象: 上の「攻撃ジャンル・属性・防御の効き」節にある「同時に phase===strike だった敵数の最大」で、0.0.9α では `全 run 中の最大 3`（上限超過 run 2 件、seed/profile: `50007/dominantLoadout`, `50017/dominantLoadout`）。0.0.8α（`git show 06eccda~1:src/qa/report.md`）では最大 2 / 超過 0 件だった。
- 原因（コード根拠）: `src/system/enemies.ts:746` の `strikeSlotsFull` はボスを枠計算から除外している（`!isBossDriven(...)`、判定は `src/system/boss.ts:110`）。一方 QA 側のメトリクス（`src/qa/simulation.test.ts:602`）はボスを含む全敵の `phase === "strike"` を単純カウントしている。つまり「ボス 1 体が strike 中 + 取り巻き非ボス 2 体が上限いっぱいまで strike」で合計 3 体になり、`ENEMY_AI.maxSimultaneousStrikers=2`（`src/data/tuning.ts:896`）と比較すると「超過」に見えるが、ゲームロジック側は設計通り（`enemies.ts:743-745` のコメント参照）に動いている可能性が高い。
- 未確認点: 実際に該当 seed のボスがどれか（kingSlime か別ボスか）、プレイ感として 3 体同時 telegraph が過負荷かどうかは未検証。次回 QA では `QA_DEBUG=1` 相当のログか専用カウンタで「ボス除外後の非ボス striking 数」を別集計し、真の上限超過かどうかを切り分けるとよい。
- 直すなら誰が: 計測を直すなら `src/qa/simulation.test.ts`（QA 担当）。ボス戦中の 3 体同時テレグラフが体感的にきつい場合の難度調整は `src/data/tuning.ts` の `ENEMY_AI.maxSimultaneousStrikers` または該当ボスの取り巻きスポーン数（`system/boss*.ts` 側）。
